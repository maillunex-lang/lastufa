# Архитектура ASHENFALL: UFA

## Принципы

1. **APK = движок + ядро + загрузчик.** Всё, что можно описать данными (предметы, заражённые, регионы, локации, лут, правила, ассеты), живёт в пакетах и обновляется без пересборки APK.
2. **Системы не знают друг о друге напрямую.** Факты публикуются в `EventBus`, состояние живёт в системах сессии, сцена — лишь представление.
3. **Симуляция отделена от рендера.** Системы сессии (`AfSurvival`, `AfWorldMap`, `AfWeather`…) — это `RefCounted` без узлов; их можно тестировать headless, «перематывать» и в будущем синхронизировать по сети.
4. **Бюджеты вместо циклов.** Любая периодическая работа идёт через планировщик с бюджетом кадра и профилем устройства.
5. **Ничего не теряется.** Сохранения атомарны и проверяются хешем; контент из удалённого пакета остаётся в сохранении «недоступным».

## Время и симуляция

- `Clock`: 1 реальная секунда = 1 игровая минута при 1×; скорости 1×/2×/4×. Пауза — **стек причин** (`panel:*`, `dialog:*`, `map`, `user`, `death`): время идёт, только когда причин нет. Любая модальная панель/диалог — «момент решения», время стоит.
- `Scheduler`: задача = (имя, уровень, интервал в игровых минутах, макс. шаг). Время накапливается по задачам; готовые выполняются по кругу, пока не исчерпан **бюджет кадра** профиля (2–4 мс). Первые запуски разнесены случайной фазой — нет синхронных всплесков. Интервалы региональных/стратегических задач умножаются на `sim_interval_mult` профиля.
- Уровни: `LOCAL` (потребности, порча, автосохранение), `REGIONAL` (погода), `STRATEGIC` (миграция заражённых между районами). ИИ заражённых в локации — отдельный LOD (ниже).
- `fast_forward(minutes, chunk, tiers)`: синхронная перемотка для сна, путешествий, офлайна.
- **Офлайн-прогресс**: 1 реальная минута = 1 игровая, максимум 24 игровых часа; выполняются региональные и стратегические задачи, потребности героя считаются одним шагом с защитным порогом 25 (герой не может умереть, пока игра закрыта). Отчёт «Пока вас не было» строится из журнала.

## ИИ заражённых и производительность в локации

- `AfZombieManager` каждые 0,5 с сортирует живых по расстоянию: активны только ближайшие `max_active_zombies` (10/20/36), остальные заморожены, но видимы.
- Близкие (< 20 м) «думают» каждый физический кадр (30 Гц), дальние — раз в `ai_far_think_interval` кадров со сдвигом слота.
- Восприятие: зрение (дальность × погода × ночь × скрытность героя × фонарь, конус FOV, луч прямой видимости), слух (событие шума с радиусом × слух типа × погода), обоняние (короткая дистанция), память (`memory_sec`), групповая тревога (стон при обнаружении), засада (затаившиеся просыпаются вблизи или от громкого шума).
- Навигация: навмеш запекается в фоне из статических коллайдеров; до готовности — прямое следование. Вблизи цели — прямое преследование (дешевле).
- Пул объектов заражённых; трупы — контейнеры лута, максимум 12, старые возвращаются в пул.
- Профили также задают тени, частицы, масштаб 3D-рендера, MSAA, лимит FPS, число динамических источников света, дальность видимости пропсов, окклюдеры, бюджет кэша ассетов. `Perf` понижает масштаб рендера при устойчивых просадках (косвенный признак перегрева; прямого API температуры в Godot нет).

## Хранение данных

- **Системная БД** `user://system.db`: `packages`, `package_files`, `package_history`, `download_jobs`, `downloads`, `kv`. Миграции через `PRAGMA user_version`.
- **Сохранение** = отдельная SQLite-БД на слот. Каждая система реализует интерфейс *Persistable*:
  `save_key()`, `schema_sql()`, `save_to_db(db)`, `load_from_db(db)` и хранит данные в своих таблицах (`clock`, `player`, `inventory_items`, `regions`, `world_state`, `weather`, `journal`, `location_state`, `container_state`, `rule_state`, `meta`).
- Запись: новый `world.db.tmp` в одной транзакции → SHA-256 → старый файл в `backups/` (3 последних) → атомарное переименование → `meta.json`. Загрузка: проверка хеша, при порче — самая свежая целая копия; работа идёт на копии файла; миграции формата (`saves/save_migrations.gd`); отчёт о недостающих пакетах.
- `user://session.lock` пишется при старте сессии и удаляется при штатном завершении; если он есть при запуске — предлагается восстановление из автосохранения. Автосохранение также при уходе приложения в фон (Android).
- Конфигурации и игровые описания — JSON в пакетах.

## Контент и моды

См. [CONTENT_DELIVERY.md](CONTENT_DELIVERY.md) и [MODDING.md](MODDING.md). Кратко: всё, что не является кодом, приходит пакетами; код из пакетов **не исполняется**, кроме подписанных официальным ключом системных `.pck` (механизм предусмотрен для будущих обновлений систем без APK).

## Готовность к кооперативу (не реализован)

Заложено: симуляция в узло-независимых системах; события шины несут только данные; состояние сериализуется в таблицы. Для кооператива потребуется: авторитетный хост, команды игрока вместо прямых вызовов, снапшоты систем по сети, сохранение только на хосте. Это задача этапа 9.

## Карта каталогов будущих модулей

Каталоги создаются, когда в них появляется работающий код, а не заранее. Планируемые модули: `construction/` (база), `population/` (жители), `vehicles/`, `economy/`, `factions/`, `diplomacy/`, `politics/`, `military/`, `medicine/`, `science/`, `infrastructure/`, `quests/`, `dialogue/`, `events/`, `localization/`, `net/` (кооператив). Каждый — отдельная система сессии + свои таблицы + свой вид данных в реестре.

## Карта

Данные — OpenStreetMap (© участники OSM, ODbL): `tools/osm_fetch.sh` скачивает выгрузки через Overpass,
`tools/osm_to_map.py` упрощает геометрию (Douglas-Peucker + shapely для валидности контуров) и пишет
`data/core/data/map/*.json`: `border`, `district` (63), `region` (населённые пункты — узлы путешествий, со
ссылками на соседей), `road`, `river`, `city_district` и `place` (Уфа). Рукотворные узлы и маршруты лежат в
`tools/map_src/` и сливаются с данными OSM. Уровни отображения (`ui/map_view.gd`): республика → район →
город → район города. Место без рукотворной локации получает детерминированную процедурную
(`world/location_generator.gd`, id `gen:<place>`); сохраняется только её состояние.
